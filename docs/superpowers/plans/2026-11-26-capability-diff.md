# Capability diff + per-widget approval (slice 9, T-010) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A re-sync review shows only per-widget capability additions/removals; the sync applies; widgets with unapproved additions are blocked ("Needs approval") until approved on their card; a change already shown is never asked again.

**Architecture:** Pure capability math (manifest set ops + `sync::capability_changes`/`sync::merge_approval`) feeds `plan_sync`/`apply_sync`. A new `seen_capabilities` column records what the user has been shown; pending(w) = seen(w) − approved(w) drives a new `PlacementStatus::NeedsApproval`. A new `approve_widget(name)` command approves pending(name) from the stored snapshot. The frontend renders the diff and the blocked card; it sends only names and a bool.

**Tech Stack:** Rust (pharos-manifest, pharos-engine, rusqlite_migration, Tauri 2 + tauri-specta rc.26), SolidJS + vitest.

**Spec:** `docs/superpowers/specs/2026-11-26-capability-diff-design.md`

## Global Constraints

- `pharos-manifest` / `pharos-engine` never depend on Tauri.
- Frontend sends only widget names and a bool; what is approved is derived by the engine from the stored snapshot / held plan.
- Run-time checks against the approved set (http/command/file) stay unchanged as the backstop.
- Migrations via `rusqlite_migration` (`user_version`); new file `005_seen_capabilities.sql`.
- `app/src/bindings.ts` is regenerated by `cargo test`, never hand-edited.
- Diff, pending and approval are per **leaf** widget; container entries are stored but never diffed, pending or approved on their own.
- Removals never need consent. Approval is per widget, never per item.
- No browser `prompt()`/`alert()`.
- Gates at the end of every task: `cargo fmt --all --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test`, `npm run typecheck -w app`, `npm test -w app`.

## Review Focus

1. **Existing installs after upgrade** — users who approved everything before slice 9 must not be re-asked: migration backfills `seen_capabilities` from `approved_capabilities`. Test in Task 2 (`migration_005_backfills_seen_from_approved`).
2. **First sync declined** — `apply_sync(false)` on a first sync applies, every leaf with capabilities is blocked, static widgets still render. Test in Task 3 (`first_sync_applied_without_approval_blocks_capable_widgets`).
3. **Old pending change + a new one** — review lists only the new host; *Approve and apply* approves only that; the older seen-but-unapproved host stays pending. Test in Task 2 (`approve_and_apply_covers_only_what_was_shown`).
4. **Widget removed then re-added with the same capabilities** — its approval is dropped on removal and asked again on return. Test in Task 2 (`removed_widget_loses_its_approval`).
5. **`approve_widget` while a sync is pending review** — approves the stored snapshot's pending set, never the held plan's capabilities. Test in Task 3 (`approve_widget_uses_the_stored_snapshot_not_the_pending_plan`).

### Task 1: Capability math (pure)

**Files:**
- Modify: `crates/pharos-manifest/src/capabilities.rs` (`impl Capabilities`, tests module)
- Modify: `crates/pharos-engine/src/sync.rs` (new type + two fns + tests)

**Interfaces:**
- Produces:
  - `Capabilities::minus(&self, other: &Capabilities) -> Capabilities` and `Capabilities::intersect(&self, other: &Capabilities) -> Capabilities` — destructure exhaustively, like `extend`.
  - `pub struct CapabilityChange { pub added: Capabilities, pub removed: Capabilities }` in `sync.rs`, deriving `Debug, Clone, Default, PartialEq, Eq, Serialize` + `specta::Type` behind the feature; re-exported from the engine crate root next to `SyncPlan`.
  - `pub(crate) fn capability_changes(approved: &CapabilitySet, seen: &CapabilitySet, new: &CapabilitySet, containers: &BTreeSet<String>) -> BTreeMap<String, CapabilityChange>`
  - `pub(crate) fn merge_approval(approved: &CapabilitySet, new: &CapabilitySet, changes: &BTreeMap<String, CapabilityChange>, approve: bool) -> CapabilitySet`

Rules (from the spec): for each widget `w` in `new` not in `containers`: `added = new(w) − (approved(w) ∪ seen(w))`, `removed = approved(w) − new(w)`; omit when both empty. Widgets absent from `new` are omitted (they show under Widgets: removed). `merge_approval`: for each `w` in `new`: `approved(w) ∩ new(w)`, plus `changes[w].added` when `approve`; drop empty entries; widgets absent from `new` drop out.

  - `removals_are_reported_without_additions`: approved `a:{hosts:[h1,h2]}`, new `a:{hosts:[h1]}` → `added` empty, `removed.hosts == {h2}`.
  - `new_widget_is_all_added_and_containers_are_skipped`: approved/seen empty, new `{leaf:{paths:[p]}, box:{paths:[p]}}`, containers `{box}` → only key `leaf`, `added.paths == {p}`.
