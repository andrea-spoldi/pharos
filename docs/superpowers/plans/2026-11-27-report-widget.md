# Report a widget to the platform team (T-023) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A blocked (Needs approval) widget's card offers **Report to platform team**, which opens a pre-filled GitHub/GitLab issue or email at the address `pharos.yaml` declares, or copies the same text when none is declared.

**Architecture:** `pharos.yaml` gains an optional `spec.support` (tagged enum, linted). The engine builds a `Report { title, body, link }` for a leaf widget's pending capabilities from the stored snapshot. A Tauri command opens the link through `tauri-plugin-opener` **from Rust only** and returns the text for the clipboard fallback. The frontend sends only the widget name.

**Tech Stack:** Rust (pharos-manifest, pharos-engine, `percent-encoding`, Tauri 2 + `tauri-plugin-opener`, tauri-specta rc.26), SolidJS + vitest.

**Spec:** `docs/superpowers/specs/2026-11-27-report-widget-design.md`

## Global Constraints

- The frontend never supplies or receives a URL to open; it sends only the widget name. No `opener:*` permission is added to `src-tauri/capabilities/default.json`.
- `pharos-manifest` / `pharos-engine` never depend on Tauri.
- The report lists exactly the widget's pending capabilities (seen − approved, as the card shows); leaf widgets only.
- Reporting changes no state: the widget stays blocked; nothing is stored.
- `app/src/bindings.ts` is regenerated by `cargo test`, never hand-edited; commit it when it changes.
- Lint snapshots: `INSTA_UPDATE=always cargo test -p pharos-manifest`, then review the `git diff`.
- Gates at the end of every task: `cargo fmt --all --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test`, `npm run typecheck -w app`, `npm test -w app`.

## Review Focus

1. **Characters that break a URL** in widget names, hosts or paths (`&`, `#`, `?`, spaces, non-ASCII) must be percent-encoded so the tracker shows the text verbatim. Test in Task 2 (`links_percent_encode_every_value`).
2. **Email bodies** must encode spaces as `%20`, not `+` (mail clients don't decode `+`). Test in Task 2 (same test, `mailto` case).
3. **A support `repo` with a trailing slash** (`https://github.com/acme/platform/`) must not produce `//issues/new`. Test in Task 2 (`trailing_slash_in_repo_is_tolerated`).
4. **Opening fails** (no default browser / mail client): the user still gets the text. The command falls back to `opened: false`. Covered by a Task 3 unit test on the outcome helper.
5. **The frontend can't open URLs**: `default.json` stays without any `opener` permission. Test in Task 3 (`frontend_capabilities_cannot_open_urls`).

### Task 2: Engine report

**Files:**
- Create: `crates/pharos-engine/src/report.rs`
- Modify: `crates/pharos-engine/src/lib.rs` (module, `EngineError`, `Engine::report_widget`, re-export), `crates/pharos-engine/Cargo.toml` (`percent-encoding = "2"`)
- Test: `report.rs` tests module, `crates/pharos-engine/tests/run.rs`

**Interfaces:**
- Consumes: `Support` (Task 1); `pending_capabilities` (lib.rs ~l.437), `Engine::platform()`, `Source.synced_commit`.
- Produces:
  - `#[derive(Debug, Clone, PartialEq, Eq, Serialize)] pub struct Report { pub title: String, pub body: String, pub link: Option<String> }` (specta behind the feature).
  - `pub(crate) fn compose(widget: &str, commit: &str, pending: &Capabilities) -> (String, String)` — title and body.
  - `pub(crate) fn link(support: &Support, title: &str, body: &str) -> String`.
  - `EngineError::NothingToReport(String)` — "widget `{0}` has no new permissions to report".
  - `Engine::report_widget(&self, name: &str) -> Result<Report>`: `UnknownWidget` if not in the stored snapshot, `NotALeaf` for a container, `NothingToReport` when its pending set is empty; `link` is `None` when the stored platform has no `support`. Never reads `self.pending`.

Exact copy (`compose`), commit = first 7 chars of `synced_commit`:
```text
title: Pharos: widget "<widget>" asks for new permissions
body:
Pharos blocked the widget `<widget>` at commit <commit>: it now asks for permissions I haven't approved.

New permissions:
- Call <host>
- Run <executable>
- Read <path>

Why I haven't approved it:

```
(one `- …` line per item, hosts then executables then paths, each sorted as stored.)

Links — every value percent-encoded with `percent_encoding::NON_ALPHANUMERIC` (so spaces are `%20`), `repo` trimmed of a trailing `/`:
- Github: `<repo>/issues/new?title=<t>&body=<b>`
- Gitlab: `<repo>/-/issues/new?issue%5Btitle%5D=<t>&issue%5Bdescription%5D=<b>`
- Email: `mailto:<address>?subject=<t>&body=<b>`

In `tests/run.rs`: `report_widget_uses_pending_capabilities_and_support` (origin `pharos.yaml` gains `support: { type: github, repo: https://github.com/acme/platform }` before the first sync; `apply_sync(false)`; `report_widget("service-catalog")` → body contains `Read catalog/services`, link starts with `https://github.com/acme/platform/issues/new?title=`); `report_widget_without_support_has_no_link`; `report_widget_refuses_unblocked_containers_and_unknown` (after `approve_widget` → `NothingToReport`; `on-call-overview` → `NotALeaf`; `nope` → `UnknownWidget`).
