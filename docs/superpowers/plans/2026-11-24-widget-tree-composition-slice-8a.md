# Widget-tree composition (slice 8a) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a developer compose a personal shell dashboard from existing widgets (including platform-authored composites), persisted across restarts, with platform dashboards untouched.

**Architecture:** "Everything is a widget, recursively" — a widget is a leaf (`spec.source` + `view`) or a container (`spec.widgets` children + layout). User dashboards are normalized SQLite rows; platform dashboards + composites stay manifest-based; the engine merges both into one `DashboardView` tree and runs leaves by a placement path. (Approach 2, D-035.)

**Tech Stack:** Rust (pharos-manifest, pharos-engine, Tauri 2, tauri-specta, rusqlite/rusqlite_migration), TS (SolidJS, Vite, vitest), plain CSS tokens.

**Spec:** `docs/superpowers/specs/2026-11-24-widget-tree-composition-design.md`

## Global Constraints

- `pharos-manifest` and `pharos-engine` MUST NOT depend on Tauri; `specta` stays behind the optional `specta` feature (D-016).
- `tauri-specta`/`specta` pinned `=2.0.0-rc.26` — do not bump (D-008).
- `app/src/bindings.ts` is generated by the `export_bindings_up_to_date` test in `src-tauri/src/lib.rs` — never hand-edit. New commands MUST be added to `collect_commands!` in `specta_builder()`.
- **Per-crate test scoping until Task 6:** run `cargo test -p pharos-manifest` / `-p pharos-engine` in Tasks 1–5. A full `cargo test` regenerates `bindings.ts` from the new Rust types; that regeneration + the frontend adaptation land together in Task 6. Do not regenerate bindings before Task 6.
- Migrations are additive via `rusqlite_migration` `user_version`: add `003_dashboards.sql` to `MIGRATION_LIST`; never edit `001`/`002`.
- No `prompt()`/`alert()` — reuse `app/src/components/Dialog.tsx` (in-app dialogs only).
- Security: the frontend sends only a dashboard id, a widget name, or a placement path — never anything executable. Execution reads the stored manifest + approved capabilities (CLAUDE.md). A container's approved capabilities are the **union** of its descendants'.
- Grid is 12 columns (`GRID_COLUMNS`, D-012).

## Review Focus

- **Container cycle** (A contains B contains A): lint must reject with a precise diagnostic, and the engine's tree walk must terminate — covered in Task 1 (lint) and relied on by Task 4 (expansion). Pinned there.
- **A user placement whose widget a later sync removed:** `list_dashboards` must show it as `Missing`, never panic or drop the dashboard — Task 5 test `missing_widget_in_user_dashboard_is_missing`.
- **Stale landing id** (the landing dashboard was deleted, or a platform dashboard removed by sync): ordering/default must fall back to platform `home`, not error — Task 5 test `stale_landing_falls_back`.
- **Run-by-path still enforces consent at a nested leaf:** an unapproved host/executable/path inside a composite is denied at run time — Task 5 test `run_denies_unapproved_capability_via_path`.
- **Empty shell:** a user dashboard with no placements renders a friendly empty state, and `run`/render of it does not break — Task 7 test `empty_user_dashboard_shows_add_cta`.
