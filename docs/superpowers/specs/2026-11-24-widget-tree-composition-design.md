# Widget-tree composition (slice 8) — design

> Date: 2026-11-24 · Session S-011 · Branch `slice-8-dashboards`
> Supersedes the earlier T-009 "user dashboards + fork" framing. Status: **draft, awaiting approval.**

## Intent and why

Today a dashboard is a read-only thing the platform repo ships (`kind: Dashboard`,
rendered from the synced snapshot). Slice 8 turns the developer from a viewer into a
composer: they arrange their own **main shell** out of the widgets they care about.

The reshape that makes this clean: **everything is a widget, recursively.**

- A **leaf widget** has a `spec.source` (file / command / http) and a `view` — unchanged
  from today.
- A **container widget** has no source; it holds **children + layout** instead. The
  top-level container is the **shell** the user composes. A nested container is a
  **mini-dashboard**: a widget that groups 2–3 domain widgets (e.g. a *Kubernetes* tile =
  context + pods + recent events) so the user drops **one** thing and gets the set.

"Dashboard", "shell", and "mini-dashboard" are the same structure at different depths:
a container of placements. Either level is authorable by the platform team (in the repo)
or, eventually, by the user in-app.

**Why now:** slices 0–7 delivered the platform-curated half (sync, consent, executors,
read-only dashboards). Slice 8 is the "user-personalised" half the restart-plan promised,
and the recursive model removes the Dashboard-vs-Widget split before it calcifies.

## Goals

- The user composes a **personal shell** dashboard: add existing widgets (including
  platform-authored mini-dashboards), remove them, auto-placed on the 12-col grid, and
  it **persists across restarts**.
- **Container (composite) widgets render**, recursively, from a platform-authored manifest.
- Platform dashboards stay as read-only tabs alongside the user's shell; a re-sync never
  touches user dashboards.
- **Opt-in landing:** by default the platform `home` is the landing dashboard (D-025
  preserved); the user may opt a dashboard of theirs in as the default landing via a setting.
- The frontend still never decides what runs: the engine computes each leaf's status and
  runs it (D-024 / D-031 carried forward).

## Non-goals (this slice)

- **User-authored mini-dashboards** (a user building a composite in-app). Platform-authored
  composites render first; user authoring is slice 8b.
- **"Customize" seeding** — forking a platform dashboard's widgets into the shell as a
  starting point. Slice 8b. The shell starts empty in 8a.
- **Drag / resize.** Placement uses auto-placement only; manual layout is slice 10 (T-011).
- **Instance inputs edited in-app.** Added widgets use their declared/default inputs;
  per-instance input editing is later.

## Anti-goals (would make this a failure even if it "works")

- Reopening WASM or custom-code/UI widget bundles. v1 stays declarative
  (file/command/http); this was cut in the restart-plan and slices 0–7 depend on it.
- Letting the frontend send anything executable (URLs, args, paths, secret names) across
  IPC. A composed shell sends only *which widget by name* and *where*; execution still
  reads the stored manifest (CLAUDE.md security rule, restart-plan problem #2).
- A composite whose consent is weaker than the sum of its children. A container's
  capabilities are the **union** of its descendants'.

## Constraints

- `pharos-manifest` and `pharos-engine` must not depend on Tauri; `specta` stays behind the
  optional feature (D-016). `tauri-specta`/`specta` pinned `=2.0.0-rc.26` (D-008).
- `app/src/bindings.ts` is generated by a cargo test — never hand-edited (D-008).
- Migrations via `rusqlite_migration` `user_version`, additive (new file `003_*.sql`); never
  edit a shipped migration.
- No `prompt()`/`alert()` — reuse `Dialog.tsx` (D: in-app dialogs only).
- Capabilities derivable statically from the manifest for consent (D-010).

## Approaches considered

**1 — Manifest-native tree (one unified kind).** A widget is a leaf (`spec.source`) or a
container (`spec.widgets`); a dashboard *is* a container widget; the user's shell is stored
as a container manifest (JSON) in SQLite. *Rejected as the storage for the user shell:*
read-modify-write JSON for every add/remove/move, and it collapses the platform/user
distinction that `dashboard_templates` (read-only, re-sync-owned) vs. user rows
(user-owned) needs to keep.

**2 — Normalized shell rows + manifest composites (CHOSEN).** The user shell is normalized
rows (`dashboards` + `placements`, with `parent_id` for nesting); arrange = insert / delete /
update. Platform dashboards **and** platform composites stay manifest-based (reuse
`dashboard_templates`; add a container shape to the Widget manifest). The engine merges both
into one `DashboardView` **tree**; leaves run by a placement **path**. Row-wise edits are the
natural primitive for arrange now and for drag/resize + instance ids later; the platform
side reuses the snapshot untouched.

**3 — Flat-first.** Ship the shell as a flat placement list over leaf widgets only; defer
composite rendering a slice. *Rejected:* composites are the heart of the vision and the user
asked for platform composites to render in this slice; recursion is a modest extension of the
existing `DashboardView` builder.

## The decided design

### Manifest: container widgets (`pharos-manifest`)

Extend `WidgetSpec` so a widget is **either** a leaf **or** a container:

```rust
pub struct WidgetSpec {
    pub source: Option<Source>,          // leaf only
    pub view: Option<View>,              // was required; now None for containers
    pub widgets: Vec<Placement>,         // NEW: container children (default empty)
    pub inputs: BTreeMap<String, InputDef>,
    pub refresh: Option<String>,
    pub permissions: Permissions,
}
```

- **Leaf:** `view` present, `widgets` empty. (`source` optional = static view, as today.)
- **Container:** `widgets` non-empty, `source`/`view` absent.
- `Placement` is reused unchanged (`widget`, `x/y/w/h`, `inputs`). A container's children are
  placements referencing other widgets by name — including other containers (nesting).

**Lint (validate.rs):** reject a widget that is both (has `view`/`source` *and* `widgets`) or
neither; reject a container child naming an unknown widget; reject a **cycle** (a container
that transitively contains itself) with a precise diagnostic. Snapshot fixtures added
(insta); `examples/platform-repo` gains one composite widget so the demo has something to
drop in.

**Capability derivation (capabilities.rs):** a container contributes the **union** of its
descendant leaves' capabilities, keyed by the container's name (so consent and the slice-9
per-widget diff still work). Cycles are already refused, so the walk terminates.

### Storage: migration `003_dashboards.sql` (`pharos-engine`)

```sql
-- User-composed dashboards. Platform dashboards stay in dashboard_templates (read-only, re-sync owned).
CREATE TABLE dashboards (
    id         INTEGER PRIMARY KEY,
    name       TEXT NOT NULL,              -- route/display key, unique among user dashboards
    title      TEXT,
    position   INTEGER NOT NULL,           -- tab order among user dashboards
    created_at INTEGER NOT NULL
);

-- Placements in a user dashboard. parent_id nests one user dashboard's own layout;
-- a placement that references a *container widget* nests via the manifest, not here.
CREATE TABLE placements (
    id           INTEGER PRIMARY KEY,
    dashboard_id INTEGER NOT NULL REFERENCES dashboards (id) ON DELETE CASCADE,
    parent_id    INTEGER REFERENCES placements (id) ON DELETE CASCADE,  -- NULL = top level
    widget       TEXT NOT NULL,            -- widget name from the snapshot
    x INTEGER NOT NULL, y INTEGER NOT NULL, w INTEGER NOT NULL, h INTEGER NOT NULL,
    position     INTEGER NOT NULL,         -- order within its parent
    inputs       TEXT NOT NULL DEFAULT '{}' -- instance inputs JSON (BTreeMap<String,String>)
);
```

> `parent_id` is included now (cheap, and the schema is where nesting must be expressed)
> even though 8a only writes top-level rows — user-authored composites (8b) fill it in.

Row helpers in `db.rs` follow the `user_inputs`/`secrets_meta` precedent (plain functions,
`params!`, transactions). CRUD: `insert_dashboard`, `rename_dashboard`, `delete_dashboard`
(cascade), `list_user_dashboards`; `insert_placement`, `delete_placement`,
`placements_of(dashboard_id)`.

### Engine: one tree, two sources

`DashboardView` gains identity and a recursive child slot:

```rust
pub struct DashboardView {
    pub id: String,            // route key: "p:<name>" (platform) or "u:<id>" (user)
    pub origin: Origin,        // Platform | User
    pub editable: bool,        // user dashboards only
    pub metadata: Metadata,
    pub placements: Vec<PlacementView>,
}

pub struct PlacementView {
    pub widget: String,
    pub x: u32, pub y: u32, pub w: u32, pub h: u32,
    pub status: PlacementStatus,
    pub manifest: Option<Widget>,
    pub reads: Option<String>,
    pub children: Vec<PlacementView>,   // NEW: non-empty for container widgets
}
```

- `list_dashboards` returns platform dashboards (from `dashboard_templates`, as today) **plus**
  user dashboards (from the new rows), ordered: platform `home` first, platform by name, then
  user by `position` — **unless** a landing dashboard is set (see below), which moves that one
  to the front. Each placement whose widget resolves to a **container** has its children
  expanded recursively, with `placement_status` computed per node (a container's status is
  `Runnable` if any descendant leaf is runnable, else it surfaces the strongest child state —
  exact precedence settled by the builder, documented in `dashboard.rs`).
- **Running stays leaf-only, keyed by a path.** `run_placement(dashboard, index)` →
  `run_placement(dashboard_id: &str, path: &[usize])`. The engine re-reads the addressed
  dashboard (platform manifest or user rows), walks `path` down the placement tree to a leaf,
  re-checks its status, resolves `{{ user | inputs | secrets }}`, and runs it. Nothing
  executable crosses IPC (supersedes D-031's name+index with id+path).

### Commands (`src-tauri/src/commands.rs`, thin; regenerate bindings)

- `list_dashboards() -> Vec<DashboardView>` — signature unchanged, richer payload.
- `run_placement(dashboard_id: String, path: Vec<u32>) -> WidgetData` — re-keyed.
- `list_catalog() -> Vec<WidgetSummary>` — names/titles/kind (leaf vs container) of widgets in
  the snapshot, to populate the "add widget" picker.
- `create_dashboard(title) -> DashboardView`, `rename_dashboard(id, title)`,
  `delete_dashboard(id)`.
- `add_widget(dashboard_id, widget_name) -> DashboardView` — engine auto-places on the 12-col
  grid (first free row, default w/h from the widget's view kind) and inserts a top-level row.
- `remove_widget(dashboard_id, placement_id) -> DashboardView`.
- `set_landing(dashboard_id: Option<String>)` — opt a dashboard in as the default landing,
  stored as an `app_setting` (`home.landing` = a dashboard id; `None` clears it, back to
  platform `home`). Ordering/default-route honor it; a stale id (dashboard deleted or a
  platform dashboard removed by sync) falls back to the default.

All mutations return the fresh `DashboardView` so the frontend re-renders from engine truth.

### Frontend (`app/src`)

- `Dashboards.tsx`: route key becomes `id` not `name` (`#/d/:id`, D-025 fallback logic kept).
  Tabs list platform + user dashboards; an **editable** dashboard shows an edit affordance
  (add/remove widget, rename, delete) via `Dialog.tsx`. `WidgetFrame` slot becomes
  `{ dashboardId, path }`; a container placement renders a titled sub-grid of its `children`
  (recursively) instead of a single `WidgetFrame`.
- New: a **"+ New dashboard"** control (Dialog → title), an **"Add widget"** Dialog (pick from
  `list_catalog`), and per-placement **Remove** (confirm Dialog for destructive, Cancel-first,
  per S-008 polish). Rename/delete dashboard via Dialog. An editable dashboard also offers
  **"Set as landing"** (toggles `set_landing`); the landing one is marked in the tab bar.
- Default route: `Dashboards.tsx` lands on the engine-ordered first dashboard (which the
  landing setting may have moved to the front), keeping D-025's "unknown name → first" fallback.
- Empty shell state: a friendly "Add your first widget" notice (reuse `.notice`).

### Capabilities / consent

Adding a widget to a shell triggers no new consent: the user can only add widgets already in
the approved snapshot, whose capabilities were consented at sync. A container's union is
computed at **sync/lint** time, so dropping a composite surfaces nothing new. (Re-sync
capability diff is still slice 9 / T-010.)

## Scope split

- **Slice 8a (this design, this/next session):** everything above — manifest containers +
  lint, migration 003, engine tree+merge+run-by-path, the 6 commands, and the compose UI.
  Done when: add a widget (incl. a platform composite) to a new shell, restart → it persists
  and renders; platform dashboards unchanged; `cargo test` + `vitest` green; demo
  `docs/demos/08-user-dashboards.md` run in the real app.
- **Slice 8b (later):** user-authored mini-dashboards (write `parent_id` rows / nested
  containers), "Customize" seeding from a platform dashboard.
- **Slice 10 (T-011):** drag/resize over these same rows.

## What's left to the builder

- Exact `PlacementStatus` precedence for a **container** node (propose: `Missing` if the
  widget name is absent; else the strongest child status by the existing precedence, with
  `Runnable` if any descendant leaf runs). Document it in `dashboard.rs` and test it.
- Auto-placement algorithm specifics (default w/h per view kind; packing). Keep it simple:
  append on the first row with free width.
- Whether `create_dashboard` seeds a `name` slug from the title and how collisions among user
  dashboards are disambiguated (propose: slugify + numeric suffix).
- The plan (via `superpowers:writing-plans`) sequences 8a into steps, each ending green:
  (1) manifest containers + lint, (2) migration + db helpers, (3) engine tree + run-by-path,
  (4) commands + bindings, (5) compose UI + demo.
