# Slice 9 — capability diff on re-sync, per-widget approval (T-010)

Date: 2026-11-26 · Session: S-014 · Backlog: T-010 (resized S → M) · Follow-up: T-023 (report to platform team)

## Intent

Today any change to any widget's capabilities (even a removal) re-asks consent for the
**whole** capability set, and declining means discarding the **whole** sync (D-014, D-020).
That trains users to click "Approve" without reading, and one new host blocks unrelated
updates. Slice 9 makes consent proportional:

- the review shows **only what changed**, per widget;
- the rest of the sync applies; a widget whose new capabilities are not approved stays
  **blocked** ("Needs approval") until the user approves it in place;
- an unapproved change is **asked about once**: later syncs that carry the same change stay
  quiet and the badge remains.

Acceptance (restart-plan §5, slice 9): add a host to a widget in the repo → sync → only that
diff is asked; the widget is blocked until approved.

## Goals

- Per-widget capability diff (added / removed) against what the user has approved.
- Removals never need consent; they apply silently and show in the changelog.
- A new widget counts as all-added.
- Apply the sync while withholding approval for some widgets; those widgets don't run.
- Approve a blocked widget later, from its card, without a sync.
- No repeated asking for a change the user has already seen and not approved.

## Non-goals

- Reporting a widget to the platform team (issue/mailto/copy) — **T-023**, right after this.
- Partial approval *within* a widget (e.g. approve one of two new hosts). Approval is per widget.
- Revoking an approval the user gave earlier.
- Any change to what capabilities are (D-010/D-011) or how they are derived.

## Anti-goals

- The frontend deciding or sending capabilities. It sends widget names and a yes/no only;
  the engine derives what is approved from the **stored** snapshot (CLAUDE.md security rules).
- A run ever executing with an unapproved host/executable/path. The run-time checks against
  the approved set (http/command/file) stay as the backstop.
- Nagging: the same unapproved change re-surfacing in every review.

## Constraints

- `pharos-engine` stays Tauri-free; migrations via `rusqlite_migration`; bindings regenerated by
  `cargo test`, never hand-edited.
- Existing approvals are stored **per widget** already (`sources.approved_capabilities`,
  a `CapabilitySet` JSON) and each run looks up its own widget's approved set
  (`run_placement`, lib.rs ~954). This is what makes per-widget approval cheap.
- Lint errors still block the whole sync; a stale clone still fails with `StalePlan`.

## Approaches considered

- **A. Diff-only review, still all-or-nothing.** Review shows only changes; declining discards
  the whole sync. Small, keeps D-014 intact, but one unwanted host blocks every unrelated update
  and "blocked until approved" can't happen. Rejected.
- **B. Per-widget approval (chosen).** The sync applies; widgets with unapproved additions are
  blocked and approvable in place. Matches the slice-9 acceptance, reuses per-widget run-time
  enforcement. Costs a new placement status, an approve command and a migration. **User picked B.**
- **C. Per-widget checkboxes in the review only, no later approval.** Rejected: a user who skips
  a widget would have to wait for another sync to approve it.

## Design (decided)

### Terms
- **approved** — `sources.approved_capabilities`, what the user consented to, per widget.
- **seen** — new column `sources.seen_capabilities`: the full capability set of the last
  **applied** snapshot (migration 004; backfilled from `approved_capabilities`, since every
  sync applied so far was fully consented).
- **pending(w)** = seen(w) − approved(w): what blocks widget `w` right now.

### Plan (`plan_sync`)
`SyncPlan` gains `capability_changes: BTreeMap<widget, { added: Capabilities, removed: Capabilities }>`:
- `added` = new(w) − (approved(w) ∪ seen(w)) — only what the user has **not been shown** before
  (this is the "stay quiet" rule);
- `removed` = approved(w) − new(w);
- widgets with both sets empty are omitted;
- computed over **leaf** widgets only. A container's entry (the union of its children, D-011/8a) is
  derived data: it is stored, but never diffed, never pending and never approved on its own,
  because runs are enforced at the leaf (*builder-check call*).

`needs_consent` = any widget has a non-empty `added`. Removals alone don't set it, so a
removal-only sync is applied silently by Home (D-019) and listed in the changelog.

### Apply (`apply_sync(approve: bool)`)
- Stores the snapshot as today; `seen` := the plan's full capability set.
- `approved` is recomputed per widget in the new set:
  - `approve = true`: approved(w) := (approved(w) ∩ new(w)) ∪ added(w) — exactly what the review
    **showed**. Items seen in an earlier sync and still pending are *not* approved by this button;
    they stay blocked and are approved from the card, which shows them (*builder-check call:
    consent never covers something not on screen*);
  - `approve = false`: approved(w) := approved(w) ∩ new(w) (removals shrink it, additions are
    withheld). Widgets no longer in the repo drop out.
- `ConsentRequired` goes away: applying without approval is now legitimate.
- **Supersedes part of D-014** ("capability drift without consent refuses apply") and **D-020**
  (full set shown).

### Blocked widgets
- New `PlacementStatus::NeedsApproval { added: Capabilities }`, ordered after `Missing` and
  before `NeedsSetup`, computed by the engine from pending(leaf). `run_placement` refuses it
  with a new `ErrorKind` (`needsApproval`). For a composite/group the status sits on the leaf;
  the parent renders normally.
- New command `approve_widget(name)`: approved(name) := seen(name) — exactly pending(name), which the
  card displays.
- A renamed widget is a removal plus a new widget: its approval does not carry over and it shows
  as all-added (*builder-check call*; capabilities are keyed by name, D-011). The frontend sends only the
  name; what gets approved comes from the stored snapshot.

### UI
- **Review** (SyncReview): replaces the full capability list with "New permissions", one entry per
  widget with only its `added` items (Call / Run / Read). Removed items are listed muted under
  "No longer needed". Buttons: **Approve and apply**, **Apply, keep these blocked**, Discard.
  A first sync is the same screen with every widget's capabilities as `added`.
- **Widget card** in NeedsApproval: "Needs approval — this widget now wants to: Call `…`",
  with an **Approve** button. No confirm dialog: the card already shows exactly what is approved.
  T-023 adds "Report to platform team" next to it.
- **Changelog** gains "Permissions removed" and "Waiting for approval: <widgets>" lines.
