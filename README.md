# Local IDP

A desktop "internal developer portal" that runs on the developer's machine. A platform
team keeps one git repo of widgets, dashboards and catalog YAML; the app clones it,
validates it, asks the developer to approve what the widgets may do, and shows the result.
No server: git is both the control plane and the data plane.

```
 Platform team                          Developer laptop
 ─────────────                          ─────────────────────────────────────
 platform repo (git)  ── git fetch ──▶  Local IDP app
  ├─ cockpit.yaml                         ├─ clones the repo into app data
  ├─ widgets/*/widget.yaml                ├─ lints it and shows what changed
  ├─ dashboards/*.yaml                    ├─ asks consent for capabilities
  └─ catalog/**/*.yaml                    └─ lists (later: runs) the widgets
 CI: `cockpit lint` on every PR
```

Built with Tauri 2 (Rust) and SolidJS. Design and rationale: [`docs/restart-plan.md`](docs/restart-plan.md).

## 1. Prerequisites

| Tool | Version | Notes |
|---|---|---|
| macOS or Linux | — | Windows is out of scope for v1 |
| Rust | stable, ≥ 1.85, with `clippy` and `rustfmt` | `rustup component add clippy rustfmt` |
| Node.js | 24 (what CI uses) | npm ships with it |
| git | any recent version | the app uses the system `git`, with your SSH agent and credential helpers |

**macOS:** install the Xcode command line tools (`xcode-select --install`), which also
provide git.

**Linux (Debian/Ubuntu):** Tauri needs WebKitGTK and friends:

```sh
sudo apt-get install -y libwebkit2gtk-4.1-dev libgtk-3-dev librsvg2-dev \
  libayatana-appindicator3-dev libsoup-3.0-dev libjavascriptcoregtk-4.1-dev
```

## 2. Setup

```sh
git clone <this repo> developer-cockpit-v2 && cd developer-cockpit-v2
npm install                 # root (Tauri CLI) + the app workspace
npm run build -w app        # once: `cargo test` embeds app/dist via tauri::generate_context!
cargo test                  # all Rust tests; also regenerates app/src/bindings.ts
npm run dev                 # starts Vite + the Tauri window (first build takes a few minutes)
```

`npm run dev` opens a window titled **Local IDP**. On a fresh install it shows
**Connect your platform repo**.

## 3. Everyday commands

| Command | Does |
|---|---|
| `npm run dev` | Run the app with hot reload (`tauri dev`) |
| `cargo test` | Rust tests; regenerates `app/src/bindings.ts` from the Tauri commands |
| `cargo clippy --all-targets` | Rust lint (all clippy warnings are errors) |
| `cargo fmt --all` | Format Rust |
| `npm test -w app` | Frontend tests (vitest) |
| `npm run typecheck -w app` | `tsc --noEmit` |
| `npm run check` | Typecheck + frontend tests |
| `cargo run -p cockpit-cli -- lint <repo> [--format json]` | Validate a platform repo, as platform CI would |
| `INSTA_UPDATE=always cargo test -p cockpit-manifest` | Accept lint snapshot changes, then review `git diff` |

CI (`.github/workflows/ci.yml`) runs all of the above on macOS and Ubuntu and fails if
`app/src/bindings.ts` differs from what `cargo test` generates. Never edit that file by hand.

## 5. Walkthrough

The demo plays both roles: the **platform team** writing and linting the repo, and a
**developer** connecting to it in the app. It takes about 10 minutes. Paths below use
`/tmp/platform` as the platform repo; any directory works.

### 5.1 The platform repo and `cockpit lint`

`examples/platform-repo` is what a platform team would maintain:

```
cockpit.yaml                         kind: Platform (inputs, secrets, discovery dirs)
widgets/welcome/widget.yaml          static markdown, no data source
widgets/k8s-context/widget.yaml      runs `kubectl`
widgets/my-pipelines/widget.yaml     calls the GitLab API
widgets/service-catalog/widget.yaml  reads catalog/services/*.yaml
dashboards/home.yaml                 kind: Dashboard (12-column grid)
catalog/services, catalog/teams      catalog data as YAML
```

1. Lint it:

   ```sh
   cargo run -q -p cockpit-cli -- lint examples/platform-repo
   ```

   → `4 widgets, 1 dashboard, 4 catalog files: 0 errors, 0 warnings`, followed by the
   **capability summary**, which is what developers will be asked to approve:
   `k8s-context` runs `kubectl`, `my-pipelines` calls `https://gitlab.com`,
   `service-catalog` reads `catalog/services`. Nobody declares these by hand; they are
   derived from each widget's `spec.source`.

2. Break it in a copy:

   ```sh
   rm -rf /tmp/broken && cp -r examples/platform-repo /tmp/broken
   sed -i '' 's#../../catalog/services/#../../../../etc#' /tmp/broken/widgets/service-catalog/widget.yaml
   cargo run -q -p cockpit-cli -- lint /tmp/broken; echo "exit $?"
   ```

   → `error: widgets/service-catalog/widget.yaml: spec.source.path: `../../../../etc`: path escapes the repository root [path-escape]`
   and `exit 1`. `--format json` prints the same finding for tooling.
   (On Linux, use `sed -i` without the `''`.)

### 5.2 Prepare a repo for the app

The app clones from a URL or a local path. Make a local git repo from the example, and
start from a fresh app state:

```sh
rm -rf /tmp/platform && cp -r examples/platform-repo /tmp/platform
git -C /tmp/platform init -q -b main
git -C /tmp/platform add -A && git -C /tmp/platform commit -qm init

# Dev builds keep their state here (Linux: ~/.local/share/dev.cockpit.local-idp)
rm -rf ~/Library/Application\ Support/dev.cockpit.local-idp

npm run dev
```

### 5.3 Onboarding

1. The window shows **Connect your platform repo**, then `✓ git version …` once the
   app has found git. The branch field says `main`; **Connect** stays disabled until a URL
   is typed. (Without git on `PATH` you get **git was not found** with install
   instructions and a **Check again** button.)
2. Type `/tmp/nope` → **Connect** → **git could not clone the repository**, showing
   git's own message (`repository '/tmp/nope' does not exist`) and a hint about SSH host
   keys. The form is usable again.
3. Type `ext::sh -c touch% /tmp/pwned` → **Connect** → `transport 'ext' not allowed`.
   `ls /tmp/pwned` confirms nothing ran: git may only use `file`, `git`, `http(s)` and
   `ssh`.
4. Type `/tmp/platform` with branch `-x` → **That branch name isn't valid**.
5. Set the branch back to `main` → **Connect**. The button reads **Cloning…**, then the
   app moves on to the review. `~/…` paths work as well; they are expanded before git
   sees them.

### 5.4 First sync: review and consent

6. **Review the platform repo** shows:
   - `Widgets: added k8s-context, my-pipelines, service-catalog, welcome`
   - `Dashboards: added home`, and `Platform settings changed`
   - **What these widgets can do on your machine**: k8s-context *Run* `kubectl`,
     my-pipelines *Call* `https://gitlab.com`, service-catalog *Read* `catalog/services`
7. **Discard** → *Nothing from the platform repo is applied yet.* → **Review the repo**
   brings the same review back. Quitting and relaunching also skips onboarding and
   comes back to this review, because nothing has been applied yet.
8. **Approve and apply** → the header shows `/tmp/platform · main · <short sha>` and
   **Widgets** lists four cards, e.g. *Kubernetes Context* · `k8s-context` · raw view ·
   command · kubectl.

### 5.5 Later syncs: Sync now and the changelog

Keep the app open and edit `/tmp/platform` from a terminal between steps, as the
platform team would by merging to `main`.

9. **Sync now** with nothing changed → *Already up to date.*
10. A change that doesn't touch capabilities is applied without asking:

    ```sh
    sed -i '' 's/title: Welcome/title: Hello/' /tmp/platform/widgets/welcome/widget.yaml
    git -C /tmp/platform commit -qam retitle
    ```

    **Sync now** → no review; a **Synced to `<sha>`** changelog says
    `Widgets: changed welcome`, and the card now reads *Hello*.
11. A new capability needs consent again:

    ```sh
    printf '  permissions:\n    hosts: ["https://status.acme.dev"]\n' >> /tmp/platform/widgets/my-pipelines/widget.yaml
    git -C /tmp/platform commit -qam host
    ```

    **Sync now** → **Review changes** with my-pipelines *Call*
    `https://gitlab.com, https://status.acme.dev`. (This is the widget's full set; showing
    only the new host is slice 9.) **Discard** → back to the list, still on the previous
    commit. **Sync now** → the same review → **Approve and apply** → changelog.
12. A broken repo is never applied:

    ```sh
    sed -i '' 's#../../catalog/services/#../../../../etc#' /tmp/platform/widgets/service-catalog/widget.yaml
    git -C /tmp/platform commit -qam break
    ```

    **Sync now** → **1 lint error: this version can't be applied**, listing
    `widgets/service-catalog/widget.yaml spec.source.path`, with no apply button.
    **Discard** → the last good widgets are still listed.
13. Quit and relaunch. The app syncs on launch without blocking: the widget list appears
    right away, and the same lint review follows once the fetch has finished.

To start over, quit the app and repeat 5.2.

## 6. How trust works

- **Capabilities are derived, not declared.** Hosts, executables and repo paths come
  from each widget's `spec.source`. `spec.permissions` can only add hosts.
- **One approval per capability set.** The app stores a hash of the set you approved.
  A sync with the same set applies silently; any change shows the review again.
- **The frontend can't forge a sync.** The plan lives in the Rust engine between
  review and apply; the UI only sends "apply, with consent: yes/no". Apply refuses
  if the repo has lint errors, if the clone moved since the review, or if consent is
  missing.
- **Files on disk match what was approved.** Discard resets the clone to the last
  applied commit.
- **git can't hang or escape.** Every call runs with stdin closed, no terminal prompts,
  SSH in batch mode (unless you configured your own SSH command) and a 120 s timeout.
  Only the `file`, `git`, `http(s)` and `ssh` transports are allowed.
- **Strict CSP.** The production webview loads only the app's own scripts and styles.

Slice 3 adds execution-time enforcement against the approved set; see
`docs/restart-plan.md` §3.

## 7. Troubleshooting

| Symptom | Cause / fix |
|---|---|
| `cargo test` fails in `generate_context!` about a missing `dist` folder | Run `npm run build -w app` once |
| CI fails on `git diff -- app/src/bindings.ts` | Run `cargo test` and commit the regenerated file |
| **git could not clone** with `Host key verification failed` | The app never prompts. Run `ssh -T git@<host>` once in a terminal to accept the host key |
| `Permission denied (publickey)` | Load your key into the agent (`ssh-add`); passphrase prompts are disabled inside the app |
| **git took too long and was stopped** | A git call ran over 120 s; check the network or VPN and retry |
| A private HTTPS repo fails to authenticate | Set up a git credential helper in a terminal first; the app has no login prompt |
| The app opens on an old state | Quit and delete the app data folder from 5.2 |
